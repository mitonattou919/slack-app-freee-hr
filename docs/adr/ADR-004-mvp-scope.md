# ADR-004: MVP は「後から自然言語で勤怠を登録する」機能と有給・残業申請に絞る

- **Status:** Accepted
- **Date:** 2026-09-29

---

## Context

freee人事労務 API で従業員が使える機能は多い(打刻、各種の申請、参照、承認)。
オーナーの実際の使い方では、タイムカードのようにその場で打刻はしない。「9/29 9:00〜19:00 休憩は12:00〜13:00」のように、後からまとめて登録したい。

---

## Decision

MVP でやるのは次の3つ。
1. 自然言語での勤怠登録(出退勤と休憩。一度に最大7日)
2. 有給申請(全休・午前休・午後休)
3. 残業申請(勤怠登録で所定の退勤時刻を超えたら提案する)

参照(今の勤怠、有休の残日数)は、エージェントの読み取り系ツールとして使えるようにする。

---

## Rationale

- 使われない打刻ボタンを作っても、保守の手間が増えるだけ。打刻は API が単純なので、後から足すのも簡単
- 有給は、会社で実際に使っている単位だけに絞る。時間休まで入れると、LLM が取り違えたり承認側で差し戻されたりする場面が増える
- 残業申請は勤怠登録とは別の操作にしつつ、所定を超えたら提案する。申請理由だけ本人に入力してもらう

---

## Options Compared

| Option | Pros | Cons |
|---|---|---|
| **自然言語での登録+有給・残業** (selected) | 実際の使い方に合っている | 打刻はできない |
| 打刻+自然言語での登録の両方 | 機能が多い | 使わない機能まで作ることになる |
| 申請の種類を全部入れる | 網羅できる | モーダルや検証が増えて、MVP が重くなる |

---

## Trade-offs

**Pros:**
- 機能が少なくて済み、検証を厚くできる

**Cons / Constraints:**
- 勤務時間の修正・特別休暇・月次締め・時間休の申請と承認者の操作は対象外。エージェントは freee 本体での操作を案内する

---

## Impact

エージェントの指示文とツールの構成、`LeaveType = full | morning | afternoon`。Phase 2 の候補は設計書の8章。
