# ADR-005: 勤怠は work_records API で直接更新し、上書きになる日は差分を見せる

- **Status:** Accepted
- **Date:** 2026-09-29

---

## Context

自然言語で入力された勤怠を反映する方法は2つある。
- `PUT /work_records/{date}` で直接更新する
- 勤務時間の修正申請を出し、承認されたら反映する

直接更新できるかどうかは、会社の権限設定で決まる。オーナーの会社では、従業員が自分の勤怠を直接編集できる。
なお `PUT` は**その日の勤怠を丸ごと置き換える**。

---

## Decision

- `PUT work_records` で直接更新する。修正申請に切り替える仕組みは作らない
- 登録の前に今の勤怠を取得し、確認カードに「現在 → 新規」の差分を出す。既にデータがある日には「⚠️上書き」を付ける
- 編集できない日(`is_editable=false`、締め済みなど)は、カードで「🚫」と表示し、実行するときも飛ばす
- 一度に登録できるのは最大7日(`MAX_WORK_RECORD_DAYS`)。未来の日付は受け付けない

---

## Rationale

直接編集できる会社なので、申請に切り替える仕組みは要らない。
丸ごと置き換える API なので、元のデータを誤って消してしまうのがいちばん怖い。差分を見せるのはそれを防ぐため。

---

## Options Compared

| Option | Pros | Cons |
|---|---|---|
| **差分表示+複数日(7日まで)** (selected) | まとめて入力できて、上書きにも気付ける | カードが長くなる |
| 差分表示+1日ずつ | 単純 | 1週間分を入れるのが面倒 |
| 既にデータがある日は登録させない | 安全 | 修正は freee 本体でしかできなくなる |
| 直接更新して、権限エラーなら申請に切り替える | どの会社でも使える | この会社では要らない仕組みになる |

---

## Trade-offs

**Pros:**
- すぐ反映され、承認を待たなくてよい

**Cons / Constraints:**
- 権限の厳しい会社ではそのまま使えない(その場合は修正申請の実装を足す)
- 1日分の登録はその日の値をまるごと置き換える。送っていない項目(有給の実績など)が消えるかどうかは、テスト事業所で確かめる必要がある
- API では振替出勤、振替休日、代休出勤、代休は登録できない

---

`proposals/validate.py`、`service.draft_work_records`、`executor`、確認カード。
