# ADR-001: freee は利用者ごとに OAuth 認可を取り、本人名義で操作する

- **Status:** Accepted
- **Date:** 2026-09-29

---

## Context

このボットは社内の複数人が使う。freee人事労務の申請や打刻の API は、アクセストークンの持ち主の操作として記録され、申請者も打刻者もトークンの持ち主になる。

---

## Decision

Slack ユーザーごとに freee の OAuth 認可を取り、Slack ユーザー ID と freee の従業員 ID を紐付ける。freee への操作はすべて本人のトークンで行う。

---

## Rationale

申請者が本人になっていないと、承認フローや監査の記録が成り立たない。
「まず自分だけで使う」場合でも、後から利用者ごとの紐付けを足すと大きな作り直しになるので、最初から複数人で使う前提で作る。

---

## Options Compared

| Option | Pros | Cons |
|---|---|---|
| **利用者ごとの OAuth** (selected) | 本人名義で記録が正しく残る。権限も本人の分に限られる | 連携の流れとトークンの保管・更新が必要 |
| 管理者トークン1本で代わりに操作 | 実装が簡単 | 申請者が管理者名義になる。管理者の権限で誰の勤怠でも触れてしまう |
| 自分のトークンだけ(個人ツール) | いちばん簡単 | 他の人が使えない |

---

## Trade-offs

**Pros:**
- 監査の記録と承認フローが正しく動く
- 本人に無い権限の操作はできない

**Cons / Constraints:**
- 利用者ごとにリフレッシュトークンを安全に保管し、更新する必要がある([ADR-011](ADR-011-sqlite-fernet-storage.md))
- freee のリフレッシュトークンは1回しか使えないので、同時に更新が走らないよう利用者ごとにロックする

---

## Impact

連携の流れ([ADR-002](ADR-002-oauth-oob.md))、事業所の固定([ADR-009](ADR-009-single-company.md))、`TokenProvider` の設計。
