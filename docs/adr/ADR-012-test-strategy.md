# ADR-012: 開発は freee のテスト事業所で行い、自動テストでは外部 API をモックする

- **Status:** Accepted
- **Date:** 2026-09-29

---

## Context

このボットは勤怠を上書きする。本番の事業所で試すと、実際の勤怠データを壊してしまう恐れがある。
一方で、自動テストは外部サービスに依存せず、毎回同じ結果になるようにしたい。

---

## Decision

- 開発と手動の確認は freee の**テスト事業所**で行う。`FREEE_COMPANY_ID` を差し替えれば本番に切り替わる
- 自動テストは pytest を使い、freee は `respx` で、Gemini は決まった応答を返す偽の LLM(ADK の `BaseLlm` のサブクラス)で置き換える。ADK Runner 自体は本物を通す
- Slack ハンドラは、偽の Bolt App と `AsyncMock` のクライアントで直接呼んでテストする
- 静的解析は ruff(lint と format)と mypy(strict)。`make check` でまとめて実行する
- 本人チェックや二重実行の防止といった安全策は、わざと壊してテストが失敗することを確かめる

---

## Rationale

安全策が本当に効いているかを、外部サービスなしで毎回確かめられる。
実際の API の癖(レスポンスの形やエラーの形式)は、テスト事業所で確かめる。

---

## Options Compared

| Option | Pros | Cons |
|---|---|---|
| **テスト事業所+モック** (selected) | 安全で、結果が毎回同じ | モックと実際の API がずれる恐れ |
| 本番の事業所で自分の勤怠を使って試す | 準備が要らない | 実際のデータを壊す恐れ |
| TDD で書き進める | 設計が良くなる | オーナーが選ばなかった |

---

## Trade-offs

**Pros:**
- 82件のテスト、カバレッジ約 89%。起動処理(`main.py`)と設定の読み込み(`config.py`)はテストしていない

**Cons / Constraints:**
- 手動で確かめることが残る(下の表)

**テスト事業所で手動で確かめる項目:**

| # | 手順 | 期待する結果 |
|---|---|---|
| 1 | DM → 連携 → OOB のコードを貼る | 連携が完了する |
| 2 | 「昨日 9:00〜19:00 休憩12-13」→ 登録 | freee の画面に反映される |
| 3 | 既にデータがある日にもう一度登録し、キャンセル | ⚠️上書きと表示され、キャンセルなら何も変わらない |
| 4 | 「月〜金 9-18」と、8日分の指定 | 5日分のカードが出る。8日分は上限エラー |
| 5 | 9-21 で登録 → 残業申請の提案 → 理由を入力 | freee に残業申請ができる |
| 6 | 「来週金曜 午前休」→ 経路を選ぶ | freee に有給申請ができる |
| 7 | 他の人がボタンを押す/15分たってから押す | 断られる |

合わせて確かめること:`prompt=select_company` と OOB 方式の組み合わせ、1日分の勤怠 PUT で有給の実績が消えないか、今の Gemini のモデル名。

---

## Impact

`tests/`、`Makefile`(`check`、`typecheck`)、`pyproject.toml` の開発用の依存関係。
