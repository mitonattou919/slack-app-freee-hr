# ADR-007: LLM は案を作るだけにして、書き込みは本人がボタンを押したときにコードが行う

- **Status:** Accepted
- **Date:** 2026-09-29

---

## Context

エージェントを入口にすると、LLM が誤って解釈したり、ありもしない内容を作ったりして、勤怠や申請が勝手に書き換わる恐れがある。
勤怠データは給与に直結するので、誤った書き込みは影響が大きい。

---

## Decision

- 書き込み系のツール(`propose_*`)は、検証して Proposal を DB に保存するところで止める。freee には書き込まない
- Slack に確認カードを出し、**本人が「登録する/申請する」を押したときだけ**、アプリのコード(`executor`)が freee に書き込む
- ボタンが押されたら、押した人が持ち主か、有効期限内(15分)か、まだ `pending` かを確認する。状態は `pending → executing` へアトミックに遷移させ、二重に実行されないようにする
- ボタンの値には `proposal_id` だけを入れ、中身は DB から読む
- 承認経路は LLM に選ばせない([ADR-010](ADR-010-approval-route-selection.md))
- 読み取り系のツールは LLM が自由に呼んでよい

---

## Rationale

LLM がどんな出力を返しても、人が確認しない限り書き込みは起きない。これを仕組みとして保証するため。
「エージェントとの会話の中で確認する」だけでは、LLM が確認を飛ばすことを防げない。

---

## Options Compared

| Option | Pros | Cons |
|---|---|---|
| **エージェントは案を作るだけ、確認はボタン** (selected) | 誤った書き込みを仕組みで防げる | 毎回ボタンを押す手間 |
| LLM は解釈だけして、あとは普通のモーダル | 単純 | ADK を使う意味が薄れる |
| エージェントが書き込みまでする(確認は会話で) | 手軽 | 誤操作を防げない |

---

## Trade-offs

**Pros:**
- 安全性をテストで確かめられる(本人チェックや同時押しのテストがあり、わざと壊すと失敗することも確認済み)

**Cons / Constraints:**
- 15分を過ぎたら依頼し直してもらう必要がある
- Proposal の状態管理が増える

---

## Impact

`proposals/`、`slack/handlers.py`、`db/repo.transition`、エージェントの指示文(「登録しました」とは言わない)。
